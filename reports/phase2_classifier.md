## 4.1 PAB-RD test 上的评测（冻结划分）

**划分**：`data/pab_rd_splits.json::test` —— 335 条 / **25 个任务组**。
train 63 组、val 9 组，与 test **任务组交集 = 0，pair_id 交集 = 0**（阶段 1 已核）。
因此这 335 条是**组干净**的独立测试集，且与 hardneg 训练集无任务重叠以外的信息泄漏源。

| 指标 | M0（任务盲，`m2_HBnt_s0`） | M1（任务感知，`m2_HB_s0`） | Δ |
|---|---|---|---|
| Accuracy | 0.7851 | **0.8537** | +6.9pp |
| **Macro-F1** | 0.7836 | **0.8501** | **+6.6pp** |
| ALLOW P / R / F1 | 0.609 / 0.722 / 0.660 | **0.750 / 0.742 / 0.746** | +8.6pp F1 |
| REVIEW P / R / F1 | 0.874 / 0.776 / 0.822 | 0.865 / **0.858** / **0.861** | +3.9pp F1 |
| **DENY（危险操作）P / R / F1** | 0.881 / **0.856** / 0.868 | **0.934 / 0.952 / 0.943** | **+9.6pp Recall** |
| 解析失败 | 0 | 0 | — |

**混淆矩阵**（行 = gold，列 = pred；三分类，support 97/134/104）：

| | M0 |  |  |  | M1 |  |  |
|---|---|---|---|---|---|---|---|
| gold \ pred | ALLOW | REVIEW | DENY | ALLOW | REVIEW | DENY |
| **ALLOW** (97) | 70 | 15 | **12** | 72 | 18 | **7** |
| **REVIEW** (134) | **30** | 104 | 0 | **19** | 115 | 0 |
| **DENY** (104) | **15** | 0 | 89 | **5** | 0 | 99 |

三条读法：

1. **危险操作的漏放从 15 条降到 5 条**（DENY→ALLOW：14.4% → 4.8%），这是任务字段最直接的收益。
2. **把 ALLOW 误判成 DENY 从 12 条降到 7 条**，同时 ALLOW 的精度从 0.609 升到 0.750——
   任务字段同时降低了两个方向的错误，不是简单的"更保守"。
3. **REVIEW 从不被误判为 DENY（两臂都是 0）**，只在 ALLOW/REVIEW 之间摇摆；
   任务盲模型把 30/134 的灰区直接放行，任务感知模型降到 19/134。

与诊断集（§1.1）对照：在真实流量上 REVIEW 输出率是 **0/37**，在 PAB-RD test 上是 0.776/0.858 的召回。
说明**灰区判定只在"参数确实来自证据块"的构造分布上成立，真实流量里模型会把它压成 ALLOW**。
这是重要的分布差异，不能混为一谈。

## 4.2 推理延迟（同硬件、同协议）

**协议**：RTX 3090 24G，fp16，单卡独占；`batch=1` 逐条 generate（greedy，max_new_tokens=6）；
预热 20 次后计时 150 次取分位；吞吐用 `bs=8`、80 条样本；显存取 `torch.cuda.max_memory_allocated()`。

| 项 | M0 | M1 |
|---|---|---|
| 冷启动（含权重加载） | 1.6 s | 1.4 s |
| 单样本延迟 mean | 340 ms | **337 ms** |
| P50 | 340 ms | 334 ms |
| **P95** | **355 ms** | **355 ms** |
| 吞吐（bs=8） | **10.9 条/s** | 10.3 条/s |
| 显存峰值 | 4042 MiB | 4128 MiB |

**两模型延迟基本相同**（差 3 ms，在噪声内），因为差别只是一个输入字段，不改变计算图。
"任务感知更贵"在本架构上不成立——这是相对"每步再调一次 7B 判官"的关键优势。

**输入长度差异必须同时报告**（否则平均延迟不可比）：

| 项 | M0 | M1 |
|---|---|---|
| mean tokens | 550 | 602 |
| P50 | 564 | 652 |
| P95 | 802 | 867 |
| max | 885 | 957 |
| >512 | 196（59%） | 215（64%） |
| >1024 | 0 | 0 |

M1 平均多 52 token（+9.5%），延迟只多 0.9%——注意力开销在这个长度区间不是瓶颈。

## 4.3 截断审计（查模型实际收到的输入）

**先说一个发现**：训练脚本的 `--max-len 1024` 对 PAB 模板**完全无效**。
`render_fitted()` 在 `style="pab"` 时直接返回模板（PAB 不含 `env_info`，没有可压缩的部分），
而 `build()` 之后**不做 ids 截断**。实测 test 集最长 957 token，从未触发 1024 上限。
所以 M0/M1 的评测是"无截断"的，这一点必须写明，否则读者会以为用了 1024 截断。

**若按 512 截断（Prompt-Guard 的常见配置），损失如下：**

| 截断到 512 | M0 | M1 |
|---|---|---|
| 受影响样本（>512） | 196 / 335（59%） | 215 / 335（64%） |
| 丢掉 `(2) Action:` 整块 | **42（12.5%）** | **122（36.4%）** |
| 丢掉 `(3) Action Input` | 56（16.7%） | 136（40.6%） |
| 丢掉结尾的 `Rating:` 作答提示 | **195（58.2%）** | **214（63.9%）** |

模板顺序是「用户请求 → 历史（Values Retrieved Earlier）→ Action → Action Input → 评分规则 → Rating:」，
**右侧截断先切掉答案提示，再切掉待判断的动作**。

这解释了一个历史疑点：P0 阶段 PG2 微调的 val Macro-F1 = 0.537，且 **val_PRA 恒为 0.5（= 随机）**。
该记录**没有保存 `args`**，无法确认当时是否用了 512 截断；但从上面的数字看，
**如果用 512，六成样本连 `Rating:` 都没了**——那 0.537 很可能至少部分是输入设计问题，而不是模型能力上限。
（当前端到端用的 `pg2_guard.py` 是 400-token 分块 + stride 64 + max 聚合，**不做截断**，不受此影响。）

**本阶段不据此改提示词**（按要求：先报告问题，不在正式测试集上反复调）。

## 4.4 阶段 2 判定

- M0 的 PAB-RD test 评测已补齐，与 M1 同协议、同划分、同测量口径。
- **任务字段的收益在分类器层面成立且方向正确**：macro-F1 +6.6pp，危险操作漏放 15→5 条，
  合法调用误杀 12→7 条。
- 延迟无实质差异（P95 都是 355 ms），"轻量"在本架构上成立。
- 截断问题已定位并量化，不改、不调，交由下一阶段决定是否重定输入预算。
