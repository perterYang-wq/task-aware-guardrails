## 2. 阶段 4 失败：为什么 workspace 不能用

`runs/ad_ws2_trace.jsonl`：643 次调用 / 26 个用户任务 / 362 个场景，**`attack_call_label == "attack"` 的数量为 0**。

根因（逐条核对）：

| 现象 | 证据 |
|---|---|
| agent 在 step 1–3 就退化 | 每任务调用数是 14/28/42（=14 个注入变体 × 1/2/3 步），最大 step **4** |
| 退化形式 | `search_calendar_events` 反复以**空 query** 调用，拿不到事件就放弃，从不推进到注入所在的文件 |
| 上下文超长 | 42 次 `maximum context length is 12288 tokens` |
| 后果 | 560 个攻击场景里没有一个执行恶意动作；所有场景 `sec=0%`，日志里 `[atk]` 行的 sec 全 0 |

不是打分管线的问题：同一套 `ad_labels.py` / `ad_pg2_v2.py` 在 banking 上正常产出 37 条攻击调用。
采集后期速度降到约 0.75 次调用/分钟（15 个任务需 8 小时），已停止并保留已完成部分。

**影响范围**：阶段 4 的全部产出（阈值、折外指标）不存在；阶段 5 失去"独立于 banking 的阈值来源"。按规则记失败，不伪造、不以 banking 冒充独立测试。

**修复方案（未执行）**：① 提高 `--max-model-len` 到 16384；② 修 workspace 的工具调用（该系统提示与函数签名对 7B 不友好，空 query 是典型征兆）；③ 或改用更适配的 agent。三条都要数小时，本次不做。

## 3. 阶段 3 结论：PG2 的信号在哪一层

### 3.1 调用级：没有信号

| 评分方式 | AUC | PR-AUC | 长度分层合并 AUC | @0.5 拦截 / 非攻击触发 |
|---|---|---|---|---|
| 截断 1000 字符 | 0.835 | 0.252 | 0.682 | 0.351 / 0.124 |
| 截断 2000 字符 | 0.713 | 0.161 | 0.392 | 0.730 / 0.321 |
| **分段取 max（模型卡）** | **0.692** | **0.148** | **0.359** | 0.649 / 0.347 |
| 参照：**直接用字符长度当分数** | **0.762** | — | — | — |

- 控制长度后 AUC 掉到 0.359–0.392，**低于随机**：同一长度层内 PG2 给攻击调用的分反而更低。
- `hist_len` 与 `step_idx` 的判别力同为 0.763 —— 在这批轨迹里 history 长度就是步数的单调函数，攻击总发生在轨迹后段。
- `corr(history 全长, PG2 分) = +0.79`。
- 任何 PG2 变体都没超过"直接用长度"的 0.762。截断 1000 的 0.835 是**轨迹级信号泄漏到调用级**（同一轨迹靠后的调用共享同一前缀，分数几乎相同）。

### 3.2 轨迹级：有信号，且干净

| 指标 | 值 |
|---|---|
| 场景级 AUC（受攻击 144 vs 无注入 16） | **0.764** |
| τ=0.5 命中受攻击场景 | 90/144 = 62.5% |
| τ=0.5 无注入场景误报 | **0/16** |
| τ=0.1 | 101/144 = 70.1%，误报 1/16 |

**解释**：PG2 判断的是"这段上下文里有没有注入话术"，不是"这一次调用是否被授权"。这条区分是本次审计最重要的结论——它同时解释了为什么调用级 AUC 看起来很糟、而场景级很干净。

## 4. 阶段 5 主表（banking，377 调用 / 160 场景）

### 4.1 一次性未调评估（τ 全部为 PG2 默认边界 0.5，从未在任何数据上调整）

| 策略 | 攻击拦截 | 严格合法中断 [95% CI] | 场景防御 | clean 场景误伤 |
|---|---|---|---|---|
| A Guard-only | 0.108 | 0.059 [0.006, 0.142] | 3/31 = 0.097 | 2/16 |
| B PG2 τ=0.5 | 0.649 | 0.150 [0.073, 0.237] | 21/31 = 0.677 | 0/16 |
| **C γ + PG2 τ=0.5** | 0.649 | **0.008** [0.000, 0.026] | 21/31 = 0.677 | 0/16 |
| D Guard + PG2 τ=0.5 | 0.649 | 0.198 [0.097, 0.304] | 21/31 = 0.677 | 2/16 |
| E γ + Guard + PG2 τ=0.5 | 0.649 | 0.067 [0.006, 0.150] | 21/31 = 0.677 | 2/16 |

聚类单位 `task_id`（16 个），B=2000，seed=0。

三个要点：
1. **γ 门是唯一让 PG2 变得可用的东西**：B → C，攻击拦截不变（0.649），合法中断从 15.0% 降到 0.8%。原因是 37 个攻击调用**全部** γ=3，而 211 个 γ=1 的读操作本来就不该被注入检测器打扰。
2. **D 与 E 都比 C 差**：Guard 在攻击侧没有任何 C 没覆盖的东西（E 的攻击拦截与 C 相同），却额外贡献 5.9% 的合法中断。**Guard 在这一批数据上被完全支配。**
3. **B 的策略在 γ=1 上误伤 17%**（36/211 的普通读操作被中断），这正是"只按 PG2 阈值做全局闸门"的典型失败。

### 4.2 嵌套分组 CV（banking 内部 5 折，按 task_id 分组，每折独立选 τ）

| 预算 | A Guard | C γ+PG2 | C 的 τ（每折） |
|---|---|---|---|
| 2% | 0.108 / 5.9% / 3·31 | **1.000 / 1.6% / 31·31** | 0.02 ×5 |
| 5% | 同上 | 1.000 / 1.6% / 31·31 | 0.02 ×5 |
| 20% | 同上 | 1.000 / 1.6% / 31·31 | 0.02 ×5 |

（格式：攻击拦截 / 严格合法中断 / 场景防御）

B、D、E 在 2%/5%/10% 预算下**全部无可行 τ**（合法中断下不去），只有 C 与 A 可行。

### 4.3 按 γ 分层的条件率（这才是运营口径）

γ=3 共 147 次调用：37 攻击 / 32 严格合法 / 78 可疑。

| 策略 | 攻击拦截 | 严格合法中断 | 可疑中断 |
|---|---|---|---|
| A Guard | 4/37 = 0.108 | 1/32 = 0.031 | 2/78 = 0.026 |
| C τ=0.02 | **37/37 = 1.000** | 4/32 = **0.125** | 78/78 = 1.000 |
| C τ=0.05 | 35/37 = 0.946 | 2/32 = 0.063 | 78/78 = 1.000 |
| C τ=0.5 | 24/37 = 0.649 | 2/32 = 0.063 | 72/78 = 0.923 |

读法：C 在 τ=0.02 的价格是**合法高影响操作 12.5% 被拦**（4/32），换来 37/37；Guard 的价格只有 3.1%，但只拦到 11%。τ=0.05 是折中点：94.6% 拦截，6.3% 误伤。

### 4.4 风险—成本曲线（banking，描述性）

| τ | C：攻击拦截 / 合法中断 / clean 误伤 / 场景防御 |
|---|---|
| 0.02 | 1.000 / 0.016 / 2/16 / 31·31 |
| **0.05** | **0.946 / 0.008 / 0/16 / 30·31** |
| 0.10 | 0.919 / 0.008 / 0/16 / 29·31 |
| 0.20 | 0.838 / 0.008 / 0/16 / 26·31 |
| 0.50 | 0.649 / 0.008 / 0/16 / 21·31 |

完整曲线见 `results/ad_v2/test_banking_curve.csv`（5 个策略 × 13 个 τ）。

## 5. 阶段 6 统计可靠性

| 项 | 做法 |
|---|---|
| 聚类单位 | `task_id`（16 个基础用户任务），同一任务的多次调用不视为独立 |
| Bootstrap | B=2000，seed=0，百分位 95% CI |
| 调用级与场景级 | 分开计算；场景防御分母 = 31（真正执行了攻击调用的场景），不是 144 |
| 不可比的口径 | 合法调用误拦率 / 合法场景中断率 / 合法任务失败率三者分列，不混用 |

**必须注意的退化区间**：C 的攻击拦截 CI 为 [1.000, 1.000]，这不是"保证 100%"，而是 16 个 task 簇里每一个都含攻击且都被拦下——样本只有 37 次攻击调用，CI 退化是样本量导致的，不能解读为稳定性证据。

## 7. 逐条回答要求的问题

**1. PG2 正确分段评分后是否仍有检测信号？**
调用级**没有**（长度分层 AUC 0.359，低于随机；所有变体都打不过"直接用长度"的 0.762）。轨迹级**有**（AUC 0.764；τ=0.5 命中 62.5% 受攻击场景，16 个无注入场景 0 误报）。正确分段（取 max）本身并不比截断 2000 字符更好（0.692 vs 0.713）。

**2. γ 是否在独立测试中降低误报？**
**没有独立测试**（workspace 标定失败），所以严格说不能回答"独立测试"。在 banking 单套件上，同 τ 下 γ 门把合法中断从 15.0% 降到 0.8%、攻击拦截不变 —— 这是"零成本收窄"，但属于同套件观察，需外部复现。

**3. 融合策略相对于 Guard-only 是否有可靠收益？**
有，且方向一致、幅度很大：场景防御 3/31 → 21/31（τ=0.5）→ 30–31/31（τ=0.05–0.02）；合法中断 5.9% → 0.8–1.6%。两组 CI 不重叠。但**"融合"其实是"替换"**：E（Guard ∪ γ∧PG2）在攻击侧与 C 完全相同，说明 Guard 的攻击覆盖被 C 完全包含，加进来只增加误伤。

**4. 哪个策略满足预先设定的成本约束？**
预算 = 合法调用中断 ≤2%。满足的只有 **C（γ+PG2）与 A（Guard）**：C 在 τ=0.02–0.5 全部满足（0.8–1.6%），Guard 5.9% **不满足**（其 CI 下界 0.6% 仍偏低，点估计超标）。B(15%)、D(19.8%)、E(6.7%) 均不满足。
**但我的预注册选优规则有缺陷**：它只最大化"攻击防御"，没把"clean 场景误伤"纳入约束，于是选出 τ=0.02（2/16 clean 误伤）。把 clean 成本算进去，**τ=0.05 更优（30/31、0/16、0.8%）**。这是规则设计问题，如实记录，不事后篡改。

**5. 是否具备启动完整在线复跑的条件？**
**不具备**。三条硬缺口：
- 没有独立于 banking 的阈值来源（workspace 失败），现在所有阈值都是在 banking 内部选的；
- 无注入场景只有 16 个，clean 侧误报的置信上界约 19%，不足以支撑部署判断；
- 执行器只过了桩测试，没接真实 pipeline；任何"security 提升"目前都是**离线拦截率的外推**，不是测出来的。

**6. 哪些结论由独立测试支持？**
- **由独立测试支持：无。** 标定失败使 banking 不能称独立测试。
- **一次性未调评估**（τ=0.5 是 PG2 官方默认边界，全程未调整）：A/B/C/D/E 的对比属于这一档，可信度中等，可作为方向性证据。
- **探索性**（数据参与过阈值选择或假设形成）：嵌套 CV 选出的 τ=0.02 的全部数字、γ 门降低误报的具体幅度、轨迹级隔离 23/31 这个数。
