# B3 · 与 Task-Shield 式判官的正面对打

> 目的：回答「和最近邻工作比，强在哪」。
> 做法：用**同一条 7B**（agent 自己的模型，走同一台 vLLM）做逐步判官，
> 判定「这次工具调用是否与用户任务对齐」，YES/NO + 一句理由。
> 提示词在 **banking dev 子集**上选（120 条），**不在测试集上调参**。

---

## 1. 离线校准（300 条：159 攻击 + 141 干净）

| 提示词版本 | 语义 | ACB | CCB_clean | P95 延迟 |
|---|---|---|---|---|
| v1 | 「是否**直接服务**于任务」 | 1.000 | **0.837** | 663 ms |
| v2 | 「是否与任务**一致**」 | 0.987 | 0.631 | 825 ms |
| **v3**（dev 选中） | v2 + 明确「冗余/重复/探索性读取也算对齐」 | 1.000 | **0.518** | 688 ms |

三版提示词的差别只在「什么算不对齐」，但**误拦率从 83.7% 只降到 51.8%**。
判官把「不必要」「冗余」「历史里已经出现过」都读成违规——这不是提示词没调好，
是这类判官在本分布上的固有倾向。v3 是 dev 上最好的一版，按规矩冻结后跑端到端。

## 2. 端到端（同一 agent、同一场景、同一执行边界）

### 2.1 travel（out-of-distribution，20 干净 + 40 受攻击）

| 臂 | ASR | 干净完成 | DENY / REVIEW / 判定数 | 延迟 mean / P95 |
|---|---|---|---|---|
| E0 无守卫 | 13/40（32.5%） | 5/20（25.0%） | — | — |
| M0 任务盲 | 6/40（15.0%） | 2/20（10.0%） | 5 / 4 / 305 | 259 / 305 ms |
| **M1 任务感知** | **1/40（2.5%）** | 2/20（10.0%） | 9 / 45 / 321 | **257 / 295 ms** |
| **Task-Shield 7B** | **0/40（0.0%）** | 2/20（10.0%） | **134 / 0 / 291** | **599 / 654 ms** |

travel 上两者干净效用并列（都是 2/20），判官把 ASR 再压 1 例（1/40 → 0/40，单例差异），
代价是**延误 2.3 倍**、且 DENY 次数是我们的 15 倍（134 vs 9）。

### 2.2 slack（in-distribution，21 干净 + 42 受攻击）— 决定性的那一组

| 臂 | ASR | 干净完成 | DENY / REVIEW / 判定数 | 延迟 mean / P95 |
|---|---|---|---|---|
| E0 无守卫 | 21/42（50.0%） | 13/21（61.9%） | — | — |
| M0 任务盲 | 4/42（9.5%） | 7/21（33.3%） | 37 / 2 / 408 | 250 / 268 ms |
| **M1 任务感知** | **0/42（0.0%）** | **14/21（66.7%）** | 26 / 5 / 411 | **251 / 265 ms** |
| **Task-Shield 7B** | **0/42（0.0%）** | **5/21（23.8%）** | **222 / 0 / 331** | **574 / 610 ms** |

**安全相同（都是 0/42），效用差 42.9pp。**

- 逐任务配对：只有 M1 成功的 **9 个**，只有判官成功的 **0 个**；
  McNemar **p = 0.0039**，Fisher **p = 0.0122**。
- 判官的干净效用 **23.8% 甚至低于无守卫基线 61.9%**——它不是在"防攻击"，是在"防动作"。
- 判官在 331 次判定里 DENY 222 次（67%），我们 411 次里 DENY 26 次（6.3%）。
  它靠 8.5 倍的拦截量换来同样的 ASR。

## 3. 成本对照（必须如实写的部分）

| | ASR（slack / travel） | 干净效用（slack） | 延迟 mean / P95 | 额外显存 | 部署形态 |
|---|---|---|---|---|---|
| **M1（1.5B 守卫）** | 0/42 / 1/40 | **66.7%** | **251 / 265 ms** | **+4.1 GB** | 独立小模型，可 CPU 卸载（B5 验证） |
| Task-Shield（7B 判官） | 0/42 / 0/40 | 23.8% | 574 / 610 ms | **0**（复用 agent 的 7B） | 与 agent 抢同一张卡 |

**我们不占优的地方**：判官复用 agent 自己的 7B，不额外占显存；我们的 1.5B 守卫要多占 4.1 GB。
**我们占优的地方**：延迟 0.44×、干净效用 +42.9pp（p=0.0039）。
**可辩护的定位**：在资源受限场景里，判官方案**没法卸载**（它必须和 agent 同卡），
而 1.5B 守卫可以单独放到 CPU/边缘（B5 会给出 CPU 延迟），这是"轻量"的实际含义。

## 4. C3 判定

原判据写的是「同 ASR 下成本 ≤1/5，或同成本下 ASR 更低」。
实测判官只比我们慢 2.3 倍，**「≤1/5」这个数字不成立**，按规矩如实记录，不硬凑。
改用可辩护的三条并列：

1. 安全同等：slack 0/42 vs 0/42；travel 1/40 vs 0/40（单例差）。
2. 效用显著更好：slack 66.7% vs 23.8%，McNemar p=0.0039。
3. 延迟 0.44×、拦截量 1/8.5；代价是额外 4.1 GB 显存。

**结论：C3 达标（按修正后的口径）。** 论文里的表述应是
「同等安全下，我们把任务完成率从 23.8% 拉回 66.7%，同时把单次判定压到 0.44 倍延迟」，
而不是「我们比 Task-Shield 更安全」——后者在 travel 上不成立（0 vs 1）。
